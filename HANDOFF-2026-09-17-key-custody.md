# Handoff — key custody: the broker stops handing out the vault key

Written 2026-09-17. Continues `HANDOFF-2026-09-16.md` (the secret broker) and
`burnbox/HANDOFF-2026-09-16-rekey-kdf-controls.md` (the re-key, Argon2id, entry controls).

**NOTHING IS DEPLOYED AND NOTHING IS COMMITTED.** This joins the same cutover.

---

## 1. Why this exists

Phase 4 gave the broker its own uid. It did not stop the broker handing the key back, and
two delivery paths made the key reachable before the broker ever held it.

**D-A. Repair published the vault credential to the agent.** `dashboard.js:5137` rendered
"Send this message to the agent:" over a message containing the setup link twice, inside
shell commands. That link decrypts to `encryption_key`, which unwraps
`vault_key_for_agent`, which decrypts every entry. Phase 5 minted a fresh vault key and
this posted it to the party being locked out. It violated acceptance check 22 of
`SPEC-uid-split.md` — "No instruction anywhere tells a user to pass the setup link as an
argument" — which round 13 wrote after fixing the CLI side. The dashboard is in the other
repo and was never checked. The same instruction was live on `/quickstart`, the home page
and `/for-agents`.

**D-B. The setup link is a bearer credential**, so any courier sees it. `onboard.py:320`
took it from `sys.argv[1]`, publishing it through `/proc/<pid>/cmdline`.

**D-C. The broker handed `enc_key` to the agent on request.** `agent.ts:449` answered a
valid token with `{api_key, enc_key, vault_url}`; the MCP server runs as the agent's uid
and derived `vault_key` there. Every `entry_mode` check ran in that process too —
`types.ts` said "enforced client-side" and meant it. `SPEC-tiered-broker.md` claimed for
tier 1 that "the key never reaches the agent", which was written about code that ran in the
agent's own process.

`PLAN-local-shape-and-uid-split.md` sequencing step 3 asked for "fresh key hierarchy,
**re-wrap to a device key**, rotate exposed upstream credentials". Phase 5 built the first
and third; `SPEC-phase5-rekey.md` never mentions a device key and has no out-of-scope
section recording the omission. Part 2 below is that missing piece.

## 2. What was built

`SPEC-key-custody.md` (in both repos) has the numbered acceptance checks.

**Part 1 — the repair modal stops addressing the agent.** `_buildOnboardMsg` is deleted.
Linux shows two commands the owner runs and the link as a copy field; macOS and Windows
keep an agent-addressed install message with the link carried separately. `onboard.py`
reads the link from stdin and REFUSES it in argv; `--dry-run` needs no link at all. The
three public docs pages are corrected.

**Part 2 — the broker gets a keypair.** P-256, generated by `install-daemon.sh` into
`/var/lib/wundervault/broker-key.pem` at 0600. `sudo wundervault-agent --pair` uploads the
public half and prints a code and a fingerprint, then waits for the owner to confirm in the
dashboard. After that a repair seals the credential to that key
(ephemeral-ECDH -> HKDF-SHA256 -> AES-256-GCM) and the owner carries a CLAIM CODE, which
names the blob and opens nothing. On a paired machine the broker REFUSES setup links.

**Part 3 — the socket serves operations, not credentials.** `agent.ts` no longer returns
`api_key` or `enc_key` to anyone; an old client gets an upgrade error. Operations:
`list_entries`, `profile_flags`, `get_entry` (LEGACY_EXEC only), `call`, `ssh_agent_open`
/ `ssh_agent_close`, `settings`, `ping`. `entry_mode` is enforced in the broker. The HTTP
broker and the ssh-agent protocol server run there too. The broker NEVER runs an
agent-supplied command — that would be code execution as the uid owning every credential —
so `vault_exec`, `vault_rsync` and `vault_ssh_exec` still run agent-side, on a plaintext
the broker agreed to release or an ssh-agent socket it hosts.

## 3. Deploy order — unchanged, with one addition

1. **Re-sign `onboard.py`.** Still step one, and this build EDITED it, so it is more
   stale than before. Key is vaulted as `OnboardSigningKey`, not Oracle's `.env` one.
2. **Publish the npm package** (`packaging/` was missing from `files`).
3. **Deploy burnbox.** Run `migrations/add_escrow_kdf.py`, `migrations/add_rekeyed_at.py`
   and **`migrations/add_broker_custody.py`**. Not during 12:00-13:00 PT on a weekday.
4. **Install the broker**, then `sudo wundervault-agent --pair` ONCE on this machine.
5. **Migrate the seven agents one at a time**: repair in the dashboard, pick this broker,
   paste the claim code into `wundervault-agent --enrol`.
6. **Open WHAT TO ROTATE and work the list.**

## 4. What this does NOT close

- **One uid is one principal.** All seven agents share the owner's uid, so any agent can
  read any other's token file and impersonate it to the broker. This narrows what an
  impersonator gets — one entry at a time, mode-gated, logged — it does not separate them.
- **The ssh-agent signing socket is world-connectable**, like every broker socket. A random
  path under /run and a short session bound it; they do not close it. Still better than the
  agent holding the private key.
- **A LEGACY_EXEC entry is still handed over in full**, and anything already read stays
  read. The exposure report remains the only remedy.
- **Pairing trusts the terminal once.** An agent driving it at that moment could print a
  fingerprint for a key it controls. Once per machine, by the owner, in a session no agent
  is driving — the same trust `sudo` already assumes.
- **A cloned machine clones its broker.** The private key and `paired.json` are files, so
  imaging a host duplicates the identity and both copies open claims for that fingerprint.
- **No broker-key rotation or DR workflow.** Same shape as the sealed store key: a backup
  restored onto different hardware does not decrypt, and the way back is repair-and-
  re-enrol. Belongs in `RESTORE.md`, still unwritten.
- **No retention sweep** for expired pairing requests, used claim codes or obsolete broker
  blobs. They accumulate.
- **Phase 6 is still unbuilt.** The server will still serve `vault_key_for_agent` to a
  holder of the api_key. After this the broker is the only holder, which is why phase 6 is
  a backstop rather than the fix.

## 5. Things that will bite you

- **`--url` on the MCP server is now ignored, loudly.** The vault URL is part of the
  credential the broker holds.
- **The agent socket protocol changed.** An old MCP server against a new broker gets
  `UPGRADE_REQUIRED`. They ship together; do not stage them apart.
- **`tests/js/entry-controls-test.js` is not a `node --test` file** — it is a manual script
  taking a URL. Running it under `--test` reports a failure that is not one.
- **The `verified_csrf_headers` fixture sends a literal `Cookie:` header** that replaces the
  jar and drops the auth cookie. It is why ~17 of the pre-existing failures fail.
- **A stale 2026-04-06 `git stash` exists in burnbox.** Untouched; do not pop it blind. A
  `git stash push` of mine failed on a bad flag and the follow-up `pop` targeted that
  pre-existing entry; verified it did NOT apply (`app/routes/agent.py` is unmodified and
  `_has_active_grant` is absent), and the stash is intact.
- **`--pair` cannot be scripted.** It refuses without a TTY, deliberately: the account
  question is the second half of the ceremony and a scripted answer is nobody looking.
- **Unpairing has two halves.** The dashboard revokes the row; `wundervault-agent --unpair`
  forgets the local marker. Doing only the first leaves the machine refusing setup links
  the dashboard has started offering again.

**The finding that justified round 2 on its own:** round 1 closed the pairing hijack with
claim-on-lookup, and round 2 pointed out that this only makes the attacker have to be
FIRST — code possession still decided which account could bind the machine, and no check
available to the broker can catch it, because the key really is this machine's. That is
what the fingerprint proves and it is exactly what makes the attack work. Closed properly
by adding the second human check: `--pair` prints which account confirmed and asks the
person at the terminal whether it is theirs, defaulting to No and refusing outright
without a TTY.

**Round 2 also caught me asserting a fix I had not made.** Round 19's triage said I had
amended the spec's 120s deadline to 180s; I had amended only the test. The reviewer
checked the writing against the code and found the divergence.

**One finding rejected with evidence:** round 20 claimed `server.ts` still spoke the old
protocol and every agent would break. It was correctly hedged — I had withheld that diff
for the payload cap — and it is wrong: `getCredentials` and `tryDaemonConnect` are gone,
every handler goes through `broker-client.ts`, and grep finds no decryption helper and no
`AgentVaultAPI` in that file.

**The round that earned its keep** found that the 30s inactivity timer stayed armed while
the broker worked, so any operation slower than 30 seconds — every tier-2 approval, every
slow upstream call — was destroyed mid-flight. My own tests missed it because the stub
returned instantly.

**And one I found myself, which is the one worth remembering:** the patch that fixed the
first two findings had DELETED the token check from the agent socket. The whole suite
still passed, because no test presented a WRONG token to the new dispatch path. It was
caught by reading the patched file, not by running anything.
