# SPEC — OAuth 1.0a as a built-in stamp (X, Tumblr, Flickr, NetSuite)

Owner, 2026-10-29: posting to X stopped working at 1.0. The `X @wundervault1 credentials` entry
holds the four X values as one JSON value; before 1.0 a program received it and signed each post
itself. 1.0 retired hand-over, and the hand-over migration turned the entry into a bearer key, so
the broker now sends the whole JSON as `Authorization: Bearer {…}` and X refuses it. Owner:
"build it now and ship it along with everything else that is pending release".

1.0 already stamps requests (SPEC-1.0-signing §F, `src/stamp.ts`): agent-described HMAC recipes
plus one named built-in, `aws-sigv4`. OAuth 1.0a cannot be written as a recipe — it signs with
HMAC-SHA1 (the recipe offers SHA-256 and up), every request needs a fresh nonce and timestamp
inside both the signed text and the header (a recipe is fixed and approved once), parameters are
percent-encoded and sorted, and it carries two public ids where a recipe has one `{key_id}`.

So: a second built-in, `oauth1`, beside `aws-sigv4`, that reads the stored four values.

## What it does

1. **Recipe.** `request.stamp = {"builtin": "oauth1"}`, with optional
   `"signature_method": "HMAC-SHA1" | "HMAC-SHA256"` (default HMAC-SHA1; NetSuite uses SHA-256)
   and optional `"realm"` (NetSuite's account id; `[A-Za-z0-9_.-]{1,64}`). No other field.
   PLAINTEXT is refused (it sends the secret). The checked recipe always carries
   `signature_method` explicitly, so `{"builtin":"oauth1"}` and
   `{"builtin":"oauth1","signature_method":"HMAC-SHA1"}` are the same recipe with the same hash
   and need one approval, not two.

2. **Stored value.** A JSON object with exactly four fields, one per role, either name allowed:
   - consumer key: `api_key` or `consumer_key`
   - consumer secret: `api_secret`, `api_key_secret` or `consumer_secret`
   - token: `access_token` or `token`
   - token secret: `access_token_secret` or `token_secret`

   (`api_key`/`api_secret`/`access_token`/`access_token_secret` are X's names and what the 09-10
   pilot stored.) Each value is a non-empty string of printable ASCII with no spaces, quotes or
   backslashes, at most 512 characters, and the stored text holds no backslash anywhere (no JSON
   escapes, so every member name is literal and a duplicate cannot hide behind `\u` spelling). Anything else is REFUSED with a message that names the
   expected field names and never echoes a value (an unknown field is counted, never named): an
   extra field, a missing role, two names for one role, one name given twice (JSON.parse would keep
   the last), an empty or non-string value, invalid JSON, or a plain secret / `{"id","secret"}`.
   Nothing is repaired. `signature_method: null` is refused, not defaulted.
   The reverse also holds: the four-field value used with any other recipe is refused (it is not
   `{"id","secret"}`), never signed whole.

3. **Signature (RFC 5849 §3.4).** Base string = `METHOD&enc(base URI)&enc(normalized params)`:
   - base URI = `https://` + lowercased host + `:port` only when the port is not 443 + the wire
     path exactly as sent (`/` when empty);
   - params = the seven `oauth_*` values (consumer_key, nonce, signature_method, timestamp, token,
     version `1.0`; never `oauth_signature` or realm) + every query parameter + the body's
     parameters **only** when the content type is `application/x-www-form-urlencoded` (a JSON body
     — X's `POST /2/tweets` — is not signed, as RFC 5849 and X require);
   - query and form values are decoded as form data (`+` is a space, `%XX` is a byte, UTF-8),
     then each name and value is percent-encoded per RFC 3986 (unreserved `A-Za-z0-9-._~` kept,
     everything else `%XX` uppercase), sorted by encoded name then encoded value, joined `k=v` with
     `&`.
   - key = `enc(consumer secret)&enc(token secret)`; HMAC-SHA1 or HMAC-SHA256; base64.

4. **Fresh every request.** `oauth_nonce` = 32 hex characters from a CSPRNG, new per call;
   `oauth_timestamp` = whole seconds now. Neither is in the recipe, so one approval covers every
   later post to the same address.

5. **Placement.** One header, `Authorization: OAuth ` + (`realm="…", ` when set) +
   `oauth_consumer_key, oauth_nonce, oauth_signature, oauth_signature_method, oauth_timestamp,
   oauth_token, oauth_version` as `name="enc(value)"` joined by `, `. Nothing goes in the query or
   body. A request that already sends an Authorization header is refused (existing rule:
   "the request already sends …, and the stamp goes there too").

6. **Refused before anything is sent:** a query or form-body parameter whose name starts with
   `oauth_` (it would be signed twice or contradict the header); a query or form body with a
   malformed `%` escape (the broker and the service would disagree on what was signed).

7. **Secrets in the reply.** The reply is scrubbed of the consumer secret, the token secret, the
   combined signing key and the signature, in every spelling the existing scrubber handles
   (as is, percent-encoded upper and lower). The two public ids (consumer key, token) travel in
   the header by design and are not scrubbed, like the AWS access key id.

8. **The secret's only uses** are the HMAC key and the scrub list — the safety argument in
   `stamp.ts`'s header comment stays true. No recipe field, part or placement reads any of the
   four values as data.

8b. **Never sent whole.** A vault_call on an entry that is NOT stamped (bearer, header, query,
   path) whose value LOOKS LIKE the bundle — a consumer-secret name and a token-secret name as
   quoted strings, any alias, valid or not — is refused before anything is sent, with
   `WRONG_KIND` and a message telling the owner to set the entry to "Signed requests" and the agent
   to call with `{"builtin":"oauth1"}`. This is the X entry's state after 1.0's migration.

9. **Approval card.** `describeRecipe` names it in words: `OAuth 1.0a (HMAC-SHA1), signed fresh
   for every request, in the Authorization header` (+ `, realm …`).

10. **Agent and owner docs.** The `vault_call` tool description lists `{builtin:"oauth1"}` beside
    aws-sigv4 and says the owner stores the four values with X's names. Site: the dashboard's
    "Signed requests" option names X and says how to store the four values; the paste recogniser
    knows the four-field shape and proposes "Signed requests"; /mcp's `request.stamp` line names
    OAuth 1.0a. MCP CHANGELOG + the site's changelog/What's new ship with the batch.

## Out of scope

The three-legged flow that mints a token (request token → authorize → access token); OAuth 2.0
refresh; oauth_body_hash; RSA-SHA1; two-legged (no token) signing; sending OAuth params in the
query or body instead of the header.

## Acceptance checks

1. OAuth Core 1.0 Appendix A.5's example (GET photos.example.net, consumer `dpf43f3p2l4k3l03`,
   with `oauth_version=1.0`) reproduces `tR3+Ty81lMeYAr/Fid0kMTYa/WM=` through the same base-string
   and signing code the broker uses.
2. X's published signing example (POST `/1.1/statuses/update.json?include_entities=true` with a
   form body, nonce `kYjzVBB8Y0ZFabxSWbWovY3uYSQ2pTgmZeNu2VS4cg`, timestamp `1318622958`)
   reproduces `hCtSmYh+iHYCEqBWrE7C7hYmtUk=` through `computeStamp`, and the header carries it as
   `oauth_signature="hCtSmYh%2BiHYCEqBWrE7C7hYmtUk%3D"`.
3. Independent cross-check: for a JSON `POST /2/tweets`, a GET whose query holds spaces, `+`,
   `%2B`, `~`, `*`, a repeated name and non-ASCII, and an HMAC-SHA256 request with a realm, the
   signature equals Python oauthlib 3.2.2's for the same inputs (fixtures generated by a script
   kept in the repo, values pinned in the test). oauthlib adds the oauth_body_hash extension for a
   non-form body; the script signs those without the body (the RFC 5849 core signature).
4. Every stored-value refusal in §2 is driven and its message contains no value.
5. A four-field value with a non-oauth1 recipe is refused; `{"id","secret"}` with oauth1 is refused.
6. Recipe refusals: unknown field, PLAINTEXT, bad realm; the omitted and explicit HMAC-SHA1
   recipes hash identically; HMAC-SHA256 hashes differently.
7. Two calls a second apart carry different nonces and the right timestamps.
8. Over a REAL https server that echoes everything back: the wire carries exactly one
   Authorization header in the §5 form and none of the two secrets or the signing key; the reply
   the agent gets contains none of them nor the signature.
9. `oauth_`-named query/body parameters and malformed `%` escapes are refused with nothing sent.
10. Through `approveStamp`, with hashes from `validateRecipe` + `recipeSha256` (the calls
    broker-ops makes): the first oauth1 call to an address asks the owner once; a second call to the
    same address with the explicit-default recipe does not ask again; HMAC-SHA256 asks again.
11. Full MCP suite passes on Node 22 and 24; mutation: removing the form-content-type check, the
    `oauth_` refusal, or the nonce freshness each fails a test.
12. Site: the recogniser test proposes "Signed requests" for the X shape and nothing for three
    fields; the dashboard option text and /mcp copy render.
