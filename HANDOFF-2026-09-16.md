# Handoff — secret broker (phase 4) and KDF agility

Written 2026-09-16. Two repos: `wundervault-mcp` (the broker) and `burnbox` (site, vault
crypto, onboarding).

**NOTHING IS DEPLOYED. NOTHING ON THIS MACHINE IS INSTALLED.** The owner's seven agents still
run against the pre-split daemon, exactly as before. Every claim below was verified in a
throwaway container or a headless browser, never on the live box.

---

## 1. What exists now

### The secret broker (`wundervault-mcp`)
The daemon has its own system account. Agents ask it for a credential over a socket and prove
who they are with a token; they cannot read the credential store or the broker's memory,
because they are a different uid. **Linux only** — macOS and Windows keep the pre-split layout
and the broker says so at every start.

Renamed in all user-facing text: it is the **secret broker**, not "the daemon". The unit name,
binary name and systemd's own vocabulary are unchanged, deliberately — renaming those breaks
upgrades for no gain.

### Enrolment is authorised by a setup link, not by local permission
`register_profile` is **deleted**, not guarded. The only way in is `enrol`, carrying a
single-use 15-minute setup link, which the broker redeems itself — so credentials never enter
the calling process. Links are accepted only from a configured origin
(`WUNDERVAULT_SETUP_ORIGIN`, default `https://wundervault.com`).

*Why that origin check is load-bearing:* without it an agent runs its own HTTP server on
loopback, serves a blob it encrypted with a passphrase it chose, and mints the one credential
the design assumes it cannot get. Every cryptographic check passes in that attack.

### Migration is repair-driven
Moving a pre-split agent across is: **REPAIR it in the dashboard, then `wundervault-agent
--enrol`**. Repair re-keys the vault, rotates credentials and issues a fresh link while
keeping the agent's identity and every vault grant.

**CORRECTED 2026-09-16 (phase 5).** This sentence used to end "so no credential is ever
carried by the migration", which was true of the credentials and FALSE of the data key.
Repair minted a new `api_key` and `encryption_key` and then re-wrapped **the same
`vault_key`** — the key that encrypts every secret in the agent's vault. Pre-split the
credential store was readable by anything running as the machine's owner, so that
`encryption_key` must be assumed known, and with the old `vault_key_for_agent` blob it yields
the `vault_key` itself. Repair did not take that back, so every secret sent to the agent
*after* a repair stayed encrypted under a key an attacker already held. Rotating the
credential closed the front door and left the lock unchanged.

Phase 5 fixes it: repair now mints a fresh `vault_key` in the browser and re-encrypts the
whole vault under it, all-or-nothing, guarded by a key epoch so a send prepared before the
repair cannot land under the retired key. See `burnbox/SPEC-phase5-rekey.md`.

**Re-keying is not the whole remedy, and the copy must not imply it is.** A plaintext an
agent already read is out permanently; no re-encryption retracts it. The dashboard's exposure
report (`/dashboard/agent-vault/exposure-report`, surfaced as the WHAT TO ROTATE banner) names
the secrets that need new values **at the provider** — which only the owner can do, and which
we cannot verify they have done.

`--migrate` lists what still needs doing; `--migrate --finish` deletes the old store and
refuses while anything is pending. Migration REFUSES off Linux, where source and destination
are the same file.

### The store key is sealed
A random 32-byte key sealed with `systemd-creds` — TPM where present, systemd's host key
otherwise — unsealed by a **non-fatal** `ExecStartPre` so a cleared TPM cannot prevent the
broker starting. Existing stores migrate automatically on first read.

**The two sealing kinds make different promises and the code says so.** TPM-sealed: a disk
copy does not open it. Host-key-sealed: systemd's key is on the same disk, so an offline copy
plus root DOES open it.

### Local destination log
Every destination an agent sends a secret to is recorded, held by the broker. `sudo
wundervault-agent --destinations` renders a self-contained page and then **deletes it**,
because the page is a copy the agents could otherwise read. `--keep` opts out.

### KDF agility (`burnbox`) — shipped, and deliberately a no-op
`users.escrow_kdf` records each account's KDF. `NULL` means PBKDF2-SHA256 600k **permanently**
— every account predating the column has NULL. The client derives from the record, never a
constant.

### Argon2id — vendored, verified, NOT switched on
`app/static/js/vendor/`, self-hosted (never a CDN — whoever can change that file can read every
passphrase typed into the site). Verified byte-identical against `argon2-cffi`. Parameters
chosen by measurement: **m=46MiB t=1 p=1**, 776ms on a throttled mid-tier phone.
`NEW_ACCOUNT_KDF` still points at PBKDF2 — flipping it is one line.

## 2. Deploy sequence — IN THIS ORDER

1. **Re-sign `onboard.py`.** It was edited, so its signature no longer matches and it refuses
   to run. The key is vaulted as **`OnboardSigningKey`** — NOT the one in Oracle's `.env`,
   which is wrong. Without this, onboarding breaks for everyone.
2. **Publish the npm package.** `packaging/` was missing from `files`, so the currently
   published package cannot be installed at all. Releases go by pushing a tag (OIDC, no npm
   token). Remember there are FIVE release surfaces.
3. **Deploy burnbox.** Setup links at 15 minutes (was 24h while claiming 15), the OS selector,
   `escrow_kdf`, the vendored Argon2id, and the phase-5 re-key. Run
   `migrations/add_escrow_kdf.py` and `migrations/add_rekeyed_at.py` — the phase-5 columns are
   also added by `run_migration()` at startup, so a restart is self-sufficient, but the
   explicit run is the runbook step. Not during 12:00–13:00 PT on a weekday.
4. **Only then install the broker here**, and migrate the seven agents one at a time.
5. **Then open WHAT TO ROTATE and work the list.** Each repair re-keys that agent's vault,
   which protects what you send it next and nothing it already read. The report names the
   credentials to replace at their providers; that is the only step that retires a leaked
   value, and nothing in the product can do it for you.

## 3. Open decisions

- **Flip `NEW_ACCOUNT_KDF` to Argon2id?** One line. Wants a real phone first — CPU throttling
  does not model the memory bandwidth a 46 MiB allocation actually meets.
- **Migrate existing accounts to Argon2id?** Designed in `CRYPTO-1.0-PLAN.md`, not built. The
  rule that keeps it safe: migrate only on a successful unlock, which is the one moment the
  passphrase legitimately exists.
- **Backup/restore for a sealed store.** A backup restored onto different hardware will not
  decrypt under a TPM-sealed key. The way back is repair-and-re-enrol each agent. Belongs in
  `RESTORE.md`; not written.
- **Resealing drill before TPM maintenance.** Same family. Not written.
- **The installer does not check its own package tree is unwritable by the agent uid.** It
  refuses an `ExecStart` under `/home`, but a world-writable global install is the same hole
  one step out.

## 4. Things that will bite you

- **`onboard.py` refuses to run when edited.** That is the tamper check working. To test
  changes, sign a copy with a throwaway key and point `ONBOARD_PUBLIC_KEY` at it — do not
  touch the real signing key, and restore `onboard.py.sig` afterwards.
- **The rehearsal container cannot materialise systemd credentials** and has no TPM firmware.
  The host-key path is verified there; the TPM branch is not verified anywhere yet. The owner's
  machine has a real TPM — that is where it gets its first honest test.
- **`systemctl` in a test will do exactly what you tell it.** A test here stopped the owner's
  live daemon because the unit name was hardcoded. It is injectable now
  (`WUNDERVAULT_OLD_UNIT`) and the suite pins it to a non-existent unit.
- **Do not test post-quantum TLS with OpenSSL 3.0.** It cannot offer ML-KEM and will report
  X25519 whatever the server supports. Use Go 1.24+, OpenSSL 3.5+, or a current browser.
  wundervault.com **already negotiates X25519MLKEM768** — verified, nothing to do.
- **`podman` rehearsal needs `--privileged`.** Without `CAP_SYS_ADMIN` systemd cannot apply the
  unit's sandboxing and the service dies with 217/USER.

## 5. Claims that are NOT true, and must not be shipped

- **"Phase 4 hardened the encryption."** It added an access boundary. The strong cryptography
  — 2SKD with a device-held Account Secret, and the client-wrapped vault key — landed in April
  2026 (`ab42e59`) and should be credited to itself.
- **"Argon2id"** — vendored and verified, but `NEW_ACCOUNT_KDF` still says PBKDF2. Nothing uses
  it yet.
- **"Sealed store"** on a machine without a TPM. Say host-key sealing, and say what it does
  not stop.
- **"Industry leading encryption."** Unverifiable from outside without an audit or a published
  white paper, and an unverifiable superlative makes a technical reader discount the
  verifiable claims beside it. `RELEASE-HIGHLIGHTS.md` has the specific true statements.

**Review history:** eight rounds on the broker (11–18) and two on the KDF work (12–13 in
burnbox's `.buildreview/`), each triaged. Rounds 15–18 were mostly finding defects in my own
earlier fixes rather than in the original build, which is where the loop stops paying.

The KDF rounds were worth their cost twice over. Round 1 found that **nothing persisted the
KDF chosen at setup** — the exact lockout the design exists to prevent, sitting inside it, and
invisible until the day someone flipped the default. Round 2 found that **removing the default
parameter had not removed the default**: `normaliseKdf` treated `undefined` as legacy, so a
missed call site or an unloaded vault-status response would derive the wrong algorithm and
present it as a wrong passphrase. Both are fixed; `undefined` now throws and `null` means
legacy explicitly.
